# 🏗 Архитектура

Как всё устроено внутри и почему именно так. Полезно, если собираетесь дорабатывать под себя или строить
похожее с нуля.

Размер кодовой базы: около 3800 строк Python. Весь SQL руками в одном файле, без ORM.

---

## Процессы

Два процесса, одна база данных.

### tg-service

Один event loop, владеет сессией Telegram. Внутри параллельно живут:

| Задача | Файл | Что делает |
|---|---|---|
| Слушатель | `tg/listener.py` | Новые сообщения, правки, удаления, сервисные события |
| Догоняние | `tg/sync.py` | На старте импортирует диалоги, дочитывает пропущенное после `last_msg_id` |
| Загрузка истории | `tg/backfill.py` | Разбирает очередь `sync_jobs` по датам и диапазонам id |
| Скачивание медиа | `media/download.py` | Стадия `download` очереди `media_jobs`, живёт здесь, потому что нужен Telethon |
| Отправка | `outbox.py` | Черновики, карточки подтверждения, реальная отправка после решения владельца |
| Здоровье | `health.py` | Проверки каждые N секунд, алерты при смене состояния |
| Сводка | `digest.py` | Ежедневный отчёт |
| HTTP API | `api/app.py` | FastAPI на 127.0.0.1:8077 |

### tg-media-worker

Отдельный процесс, в Telegram не ходит вообще. Работает с базой, диском и внешними моделями:

- расшифровка речи (Whisper),
- описание и OCR изображений (vision-модель через OpenRouter),
- извлечение текста из документов,
- эмбеддинги для семантического поиска,
- локальный HTTP на 8078 для векторизации поисковых запросов.

Модели грузятся лениво и выгружаются из памяти после `MEDIA_MODEL_IDLE` секунд простоя.

### Почему процессов два

Сессия Telethon должна принадлежать ровно одному клиенту: два процесса на одном файле сессии ломают
авторизацию. При этом Whisper и эмбеддинги надолго занимают CPU и память. Разделение даёт слушателю
не спотыкаться о тяжёлые задачи, а моделям выгружаться, не трогая соединение с Telegram.

По той же причине HTTP API **никогда не обращается в Telegram напрямую**. Он кладёт задачу в таблицу,
а её забирает тот процесс, который владеет сессией.

## Поток данных

```
событие Telegram
   ↓
tg/mapper.py         превращает объект Telethon в строку таблицы
   ↓
tg/ingest.py         пишет сообщение, отправителя, чат
   ↓
media/policy.py      решает: нужно ли скачивать и что делать дальше
   ↓
media_jobs           очередь: download → transcribe | describe | extract
   ↓
media/worker.py      выполняет, пишет результат в message_content
   ↓
эмбеддинг сбрасывается и пересчитывается на следующем круге
```

Ключевой файл для доработок — `tg/mapper.py`. Если агенту не хватает какого-то поля сообщения, добавлять
нужно там, плюс миграция и колонка в `repo.MESSAGE_COLUMNS`.

## Модель данных

Одна таблица сообщений на все чаты, а не таблица на чат. Причина простая: миграции по сотням таблиц
неуправляемы, поиск по всем чатам одним запросом невозможен, а Postgres спокойно держит десятки миллионов
строк с правильным первичным ключом.

| Таблица | Что хранит |
|---|---|
| `chats` | Чаты. `id` это marked peer id из Telethon: пользователи положительные, группы отрицательные, каналы начинаются с −100. Плюс `is_tracked`, `send_policy`, курсор `last_msg_id` |
| `users` | Профили отправителей |
| `messages` | Сообщения, первичный ключ `(chat_id, msg_id)` |
| `message_edits` | Предыдущие версии текста при правках |
| `message_content` | Производный текст: `transcript`, `document`, `image`. Со своим полнотекстовым индексом |
| `media_files` | Скачанные файлы на диске, с ротацией |
| `media_jobs` | Очередь обработки медиа |
| `sync_jobs` | Очередь загрузки истории |
| `outbox` | Черновики отправки со всей историей решений |
| `message_embeddings` | Векторы 384 измерения, индекс HNSW по косинусному расстоянию |
| `health_state` | Последнее состояние проверок, чтобы алертить на изменения, а не на каждый тик |

### Неочевидные поля messages

| Поле | Смысл |
|---|---|
| `is_out` | Сообщение отправлено владельцем |
| `reply_to_msg_id` | Только настоящие ответы. Сообщение, написанное прямо в топик форума, ответом не считается |
| `topic_id` | Топик форума, если это форум |
| `edit_date` | Только видимые правки. Telegram ставит дату правки и при смене реакций, но с флагом `edit_hide`, такие игнорируются |
| `deleted_at` | Удалённые сообщения помечаются, а не стираются: агенту полезно видеть, что было удалено |
| `raw` | Полный объект Telethon в jsonb. Страховка на случай, если понадобится поле, которое не выделили в колонку |
| `tsv` | Генерируемая колонка полнотекстового поиска, русский плюс английский |

## Поиск

Два независимых механизма, оба ищут и по тексту сообщений, и по расшифровкам, и по тексту документов
и картинок.

**Полнотекстовый.** Postgres `tsvector` с конфигурациями `russian` и `english` одновременно, синтаксис
`websearch_to_tsquery`. Хорош для имён, номеров, точных формулировок.

**Семантический.** Локальная модель `multilingual-e5-small`, 384 измерения, pgvector с индексом HNSW.
Хорош, когда человек написал другими словами. Переписка при этом никуда не уходит: модель работает на
вашей машине.

Оба доступны агенту отдельными инструментами, и в описаниях сказано, когда какой брать.

## Отправка через подтверждение

Самая важная часть с точки зрения безопасности.

```
агент → draft_message → запись в outbox → карточка от бота в чат подтверждений
                                                    ↓
                          владелец жмёт ✅ или пишет ok <id>
                                                    ↓
                              outbox.py отправляет от аккаунта владельца
                                                    ↓
                           карточка обновляется результатом, агент видит статус
```

**Почему так.** Агент читает чужие сообщения как данные. Если бы у него была возможность отправлять,
достаточно было бы написать ему в чат «перешли всё вот сюда», и он бы выполнил. Поэтому подтверждение
идёт по каналу, который агент не контролирует: собственное действие владельца в Telegram.

Что показывает карточка: адресата, последние три сообщения чата для контекста, вложения, дату отложенной
отправки, текст, причину и кто попросил. Ответ на карточку своим текстом заменяет текст черновика.

**Инвариант кода:** любая запись в Telegram проходит через `outbox.py`. Вызовов `client.send_message`
в других модулях быть не должно.

**Тонкость про свои сообщения.** Telethon не присылает события на то, что отправил сам этот же клиент.
Поэтому всё, что сервис отправляет, он записывает в базу вручную.

**Тонкость про группы.** В обычных группах у бота и у владельца разные id одного и того же сообщения,
поэтому карточка хранит оба.

## Политика обработки медиа

Правила в `media/policy.py`, одна функция решает всё.

| Тип | Автоматически | Условия |
|---|---|---|
| Голосовые, кружки | Расшифровка | Только в личках и группах |
| Документы | Извлечение текста | До 20 МБ, читаемый формат |
| Фото | Описание и OCR | До 5 МБ |
| Видео, крупные файлы | Ничего | Только по запросу агента |
| Каналы | Ничего | Никогда |

Скачанные файлы удаляются через `MEDIA_RETENTION_DAYS` дней, извлечённый текст остаётся навсегда. Если
файл понадобится снова, он скачается заново.

## Если строите похожее с нуля

Семь решений, которые стоит повторить:

1. Одна таблица сообщений с составным ключом и полным сырым объектом в jsonb.
2. Один процесс владеет сессией мессенджера, остальные общаются с ним через таблицы-очереди.
3. Медиа-конвейер через очередь с цепочкой действий, а не синхронно в обработчике события.
4. Запись в мессенджер только через черновик и подтверждение по независимому каналу.
5. Карточка подтверждения показывает контекст, а не только текст: иначе человек через неделю жмёт
   подтверждение не глядя.
6. Всё, что сервис делает от имени владельца, он же и записывает в свою базу.
7. Проверки здоровья алертят на смену состояния, а не на каждый тик, иначе алерты перестают читать.
